# 再現性監査とOpenCode Go反復計測計画（2026-07-27）

この文書は、現行正式結果の再現性に関する注意点と、追加の有料API費用を抑えて
回答生成分散・Judge分散を測る次段階の計画をまとめたものです。正式スコアや順位を
置き換える文書ではありません。

## 現行正式結果の位置づけ

READMEの正式結果は、各モデル・各シナリオにつき1会話を生成し、その会話を固定3 Judgeが
各1回評価した点推定です。複数の回答生成runを平均した値、標準偏差、信頼区間ではありません。

したがって、表の小数点以下までを再現可能な絶対値とみなしたり、1〜2ポイントまたは
1〜2位の差だけで優劣を断定したりしません。用途に関係する個別指標、Major判定、
シナリオレポートを併せて読みます。

## 固定会話のJudge再現性監査

正式15モデルの保存済み会話を変更せず、同じ3 Judgeで2回再評価しました。正式判定を含む
3測定から、モデルごとに3つのペア差を作り、15モデル × 3ペア = 45比較のnearest-rank p95を
求めました。この監査では会話を再生成していないため、観測差はJudge由来です。
p95は45個の絶対差を並べた経験的95パーセンタイルであり、母平均の95%信頼区間ではありません。

正式36シナリオ相当のモデル平均へ換算したp95は次のとおりです。

| 指標 | Base 30件の判定を変更 | Challenge 6件の判定を変更 |
|---|---:|---:|
| Role Fidelity | 1.759 | 0.209 |
| Quality | 1.506 | 0.308 |
| Persona Stability | 2.777 | 0.546 |
| Robustness | 0.000 | 9.375 |
| Recovery | 0.000 | 0.000 |
| RP Summary | 0.676 | 1.824 |
| 旧8指標平均（1〜5） | 0.073 | 0.000 |

RobustnessとRecoveryはChallengeだけから算出するため、Challenge列は6/36に薄まりません。
Recoveryのp95が0なのは、ほぼ全モデルが100に集中する天井効果も含みます。

Challengeの45比較ではMajor件数が14比較、Major-freeが12比較で変化しました。正式Baseを固定して
Challenge判定だけを差し替えた順位シミュレーションでは、最大2位の移動がありました。
MajorとMajor-freeは順位の第1・第2キーなので、連続スコアが安定していても注意が必要です。

この結果は総分散の下限です。回答生成の違いを含めると、さらに変動する可能性があります。

## 次段階の目的

追加費用を抑えながら、次の二つを分離して推定します。

1. 同じモデルが同じシナリオへ回答したときの生成分散
2. 同じ回答をJudgeが評価したときのJudge分散

最初の対象は、OpenCode Goで正式評価済みの次の6モデルです。

- Qwen3.7 Max
- Kimi K3
- DeepSeek V4 Pro
- MiniMax M3
- GLM-5.2
- MiMo V2.5 Pro

OpenCode Goは契約内の定額経路ですが、5時間・週・月単位の利用上限があります。追加残高への
自動フォールバックは使用せず、開始前にGo枠と`Use balance`設定を確認します。

## 段階A: OpenCode Judgeの校正

OpenCodeモデルをJudgeとして使った結果は、現在の正式3 Judgeによる結果と同一ではありません。
そのため、いきなり比較結果へ使用せず、保存済み会話と正式Judge成果物を使って校正します。

1. 2026-07-27時点のOpenCode Goモデル一覧を保存し、対象6モデルと同一IDではないJudge候補を選ぶ。
2. 候補例は`grok-4.5`、`hy3`、`qwen3.7-plus`、`deepseek-v4-flash`、`kimi-k2.6`などとし、
   API形式・構造化出力・Reasoning設定をpilotで確認する。
3. 保存済み正式会話を、モデル、Base/Challenge、スコア帯、Major有無で層化し、校正用と
   holdoutへ結果を見る前に分割する。
4. Judgeへ評価対象モデル名を渡さず、同じ会話を複数回評価して再現性も測る。
5. holdoutで正式Judge ensembleとのモデル平均差、順位相関、Major一致、再評価p95を確認する。

採用条件は事前に固定します。

- 構造化出力の成功率99.5%以上、打ち切り0
- Role Fidelity、Quality、Persona Stabilityのモデル平均Spearman相関0.90以上
- Role Fidelity、Quality、Persona Stabilityの平均絶対差が、上表の正式Judge再評価p95を超えない
- Major判定のCohen's kappa 0.60以上
- 特定の対象系列または自己系列だけに実用差閾値以上の系統偏りがない

この条件を満たす、対象6モデルと同一IDではない3 Judgeを固定します。条件を満たすensembleを
作れない場合、OpenCode Judgeの結果は正式比較に使わず、ここで停止します。正式Judge成果物は
校正基準であって人間による真の正解ではないため、校正合格後も結果は「探索的評価」と表示します。

## 段階B: Challenge 5生成 × 3 Judge

最初は、ユーザー発話が固定されていて有料ユーザー役を必要としないChallenge全6シナリオを
対象にします。結果を見てケースを選びません。

| 項目 | 固定値 |
|---|---:|
| 対象モデル | 6 |
| Challengeシナリオ | 6 |
| 対象モデルの独立生成 | 各5回 |
| 会話数 | 180 |
| 対象応答ターン | 810 |
| 固定OpenCode Judge | 3モデル |
| Judge出力 | 2,430 |
| OpenAI・Google・Anthropicの新規API call | 0 |

ここでの「5 × 3」は、独立した対象回答5個を、固定した異なる3 Judgeが各1回評価する設計です。
15評価を15個の独立回答として扱いません。対象回答の独立標本数は5です。Judge自身の確率的な
再現性は段階Aの反復と、必要時の事前固定追加passで別に推定します。

全対象でprompt、出力上限、Reasoning、シナリオ、Judge ensembleを統一します。新しい空の
`tmp/`出力先を生成反復ごとに使い、manifestへモデルID、API形式、時刻、設定hash、Role Pack hash、
終了理由、token usage、429履歴を保存します。429時は成功済み成果物を保持し、並列度を下げて
不足分だけ再開します。

## 統計解析と「優位な差」の定義

平均だけでなく、次をモデル・指標ごとに報告します。

- 5生成の平均、中央値、生成間標準偏差
- Judge間標準偏差とJudge別の系統差
- 生成とJudgeを階層化した95%信頼区間
- Major発生率、Major-free率、Probe成功数
- ペアごとの差、効果量、優越確率
- 各順位になる確率。単一の順位だけを結論にしない

連続指標はモデルを固定効果、シナリオをブロック、生成反復とJudgeを階層化したモデルで解析し、
bootstrapでも会話内の15評価を独立標本としてばらばらに再標本化しません。Major/Major-freeには
同じ階層を持つ二値・件数モデルを使います。

6モデルの全15ペアを比較するため、p値だけを多数並べずHolm法で多重比較を補正します。
「統計的に0と異なる」だけでなく、次の実用差も同時に満たした場合だけ優位と表現します。

| 指標 | 事前固定する最小実用差 |
|---|---:|
| Role Fidelity | 2ポイント |
| Quality | 2ポイント |
| Persona Stability | 3ポイント |
| Robustness | 10ポイント |
| RP Summary | 2ポイント |
| Major-free率 | 10ポイント |

連続指標ではHolm補正後95%信頼区間が0をまたがず、かつ差が最小実用差以上であることを
優位判定の条件とします。Major/Major-freeは二値・件数モデルで扱います。Recoveryは現在の
天井効果が強いため、初回計測では探索指標とし、優位性の主要主張には使いません。

信頼区間が0をまたいだだけでは「同等」と結論しません。同等と表現するのは、差の信頼区間全体が
上表の最小実用差の正負範囲へ収まった場合です。5生成では大きな差の検出を優先し、小さな差について
区間が広い場合は「判定不能」とします。

有意差が出なかったことも有効な結果です。データ収集の成功条件を「有意差が出ること」には
せず、180会話、810対象応答、2,430 Judge出力の完全取得、打ち切り0、事前解析の完了とします。

## 段階C: 標本追加と正式Judge確認

初回5生成で信頼区間が広すぎる場合は、良く見えたモデルだけを追加せず、同じ6モデルすべてを
5生成から10生成へ増やします。Judge分散より生成分散が大きければ生成数を増やし、Judge分散が
支配的なら全対象へ同じ追加Judge passを行います。結果を見た後にモデルごとに異なる標本数を
選びません。

OpenCode Judgeで実用差を満たす候補差が得られた場合、保存した180会話を再生成せず、正式な
GPT-5.4 mini、Gemini 3.5 Flash、Claude Haiku 4.5で全6モデルを同条件確認します。OpenAIは
通常API、GeminiとAnthropicはBatch APIを使います。直近の同規模監査usageから、2,430 callの
実効費用は約11 USDが目安ですが、実行前に保存token数から再見積もりします。この確認結果も
現行Leaderboardへ混ぜず、反復測定結果として別に公開します。

## Baseを後段にする理由

Baseは30設定 × 10往復で、動的ユーザー役として現在GPT-5.4 miniを使用します。対象モデルだけを
OpenCodeへしても、ユーザー役と正式Judgeの費用が残ります。またユーザー役をOpenCodeへ変えると、
正式プロトコルとの差へユーザー役の効果が混ざります。

そのため、まず静的入力のChallengeで生成分散とJudge代替の妥当性を確認します。その後に必要なら、
Baseについて次のどちらかを明示的に分離して実行します。

- 正式比較用: GPT-5.4 miniユーザー役を維持し、費用見積もり後に全6モデル同条件で実行
- 探索用: 固定OpenCodeユーザー役を使い、正式結果と混ぜない別実験として実行

## 公開方針

- 現行の正式スコアと順位は変更しない。
- OpenCode反復結果は、平均、標準偏差、信頼区間、標本数、Judge構成を併記する。
- OpenCode Judgeによる探索結果と正式3 Judgeによる確認結果を同じ列へ混ぜない。
- 一部モデルだけの反復平均を、単一runの正式モデルと同じLeaderboardへ混ぜない。
- シナリオ、標本数、除外、追加標本、優位判定を結果確認前にJSON/Markdownへ固定する。
